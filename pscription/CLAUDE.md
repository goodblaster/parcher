# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**pscription** is a browser script-running and page-preparation library; **pscribe** is its CLI. A "pscription" (like a doctor's ℞ — Latin *recipe*, "take thou") is an ordered list of preparation steps and scripts executed against a live page. It drives headless Chrome (chromedp), runs a pipeline of named preparation steps (dismiss dialogs, defeat lazy loading, freeze videos/canvases/cross-origin iframes to stills, embed resources as data URIs), and extracts rendered text with word-level geometry (parchmint's text layer, including its capture-time highlighting and image recording).

Serialization lives downstream: [parchmint](../parchmint) (binary `parch`) owns the capture backends (HTML, MHT, PDF, screenshots) and consumes this library for browser driving and prep. The line between the components: **pscription = live pages, parchmint = files.**

**Primary Language:** Go 1.26
**Runtime requirement:** a Chrome/Chromium installation (not bundled).

## Build & Run

```bash
go build -o bin/ ./cmd/...
./bin/pscribe https://news.site @article                  # built-in article extractor
./bin/pscribe https://shop.com dismiss.js prices.js:out   # your own scripts, capture "out"
./bin/pscribe --recipe login-and-scrape.rx https://portal.site  # .rx pscription file
./bin/pscribe --prep staticize -v https://example.com     # full prep, debug logging
```

stdout carries the JSON report (or one output raw with `--only`); logs go to stderr.

`go test ./pscription/...` covers the `.rx` parser and step grammar, and parses every embedded script with node (skipped when node is absent). The parse check exists because a script that fails to PARSE is invisible at runtime: prep steps are `stepIgnoreError`, so the exception is logged once and swallowed, and the page silently loses that step's behavior. Behavior changes are still verified by building parchmint's `parch` from this repository (one module, so changes here are picked up directly) and running its verification flow.

## Architecture

Flow: **runner** (browser session) → **pipeline** (preparation recipe) → scripts/extraction; parchmint appends its capture backend to this flow.

- **`act/`** — The action vocabulary: `act.Func`, `act.Run`, `act.Evaluate`/`EvaluateAsync`, `act.Sleep`. The one seam between this module and the browser driver; see the root CLAUDE.md.
- **`runner/`** — Browser lifecycle: chromedp context, viewport/user-agent, navigation, auto-accepted JS dialogs. `Config.PreNavigate` runs actions before the page exists (cookie seeding, evaluate-on-new-document scripts).
- **`pipeline/`** — `Step{Name, Action, ContinueOnError}`, `Recipe{Name, PreNavigate, Steps}` with per-step logging/timing. `Staticize()` is the default page-prep recipe. `Register/Lookup` step registry exists so recipes can become data (per-site overrides) without recompiling. `RewriteLinksStep(mode)` is an optional final step.
- **`pscription/`** — The `.rx` file format: parsing and running step lists, prep selection (`none`/`minimal`/`staticize`), variables, outputs.
- **`actions/`** — Composable `act.Func` building blocks (dialog dismissal, waits, server-side resource fetching/injection, media freezing, consent pre-seeding, CSP bypass). `SettleMonitor` is the exception to "composable and independent": a recipe owns one, attaches it pre-navigation, and builds its waits from it, so they share one continuous record of page activity (see the invariant below). Its unattached zero value falls back to the standalone prospective waits, which is what the step registry hands out.
- **`scripts/`** — Embedded page-context JS + the `ScriptFile` engine: JSON param injection, async detection (leading comments are stripped — a script is async iff its first code token starts `async function`; async scripts are properly awaited), dev-mode reload from disk (`PSCRIPTION_SCRIPTS_DIR`). See [SCRIPTS.md](SCRIPTS.md).
- **`agents/`** — User-agent constants. A session announces the RUNNING browser's own user agent with the headless marker removed and matching client hints (`runner.userAgentAction`); `Config.UserAgent` overrides it verbatim. It used to be a Safari string sent from Chrome — a site branching on it served Safari paths to a browser that is not Safari. The server-side fetchers ask the page for the same string (`fetchUserAgent`, once per batch) so a resource request matches the browser that loaded the page.
- **`internal/`** — config, log. Environment variables are namespaced `PSCRIPTION_*` (`_VIEW_WIDTH`, `_VIEW_HEIGHT`, `_FETCH_CONCURRENCY`, `_SCRIPTS_DIR`, `_PROFILE_SCRIPTS`) and NOTHING loads a `.env`: the bare `VIEW_WIDTH` read from a working-directory `.env` meant any project's `.env` could change a capture's viewport. Logs always go to **stderr**. `internal/log` defaults to delegating to the logos package-level logger, so external consumers get this library's logs just by configuring logos; parchmint mirrors the same pattern with its own `internal/log`.

## Dialog clearing is layered — keep this order when tuning

0. **Prevent** (pre-navigation): `actions.PreseedConsentCookies` + `PreseedConsentStorage` (localStorage via `Page.addScriptToEvaluateOnNewDocument`, runs before page JS, survives reloads). Most banners/age gates never render.
1. **Known CMPs by exact selector**: `dismiss_cmp.js` (~20 platforms incl. Usercentrics shadow DOM; Sourcepoint's cross-origin iframe is removed, not clicked).
2. **Heuristics**: `dismiss_popups.js` — visible-only clicks, overlay-scoped generic words.
3. **Demolition** at capture time: `remove_blocking_overlays.js` — geometry-based, with text-share guards so fixed heroes survive.

## Hard-won invariants (violating these caused real bugs)

Capture-backend invariants (encoder limits, PDF quirks, what Chrome's MHTML writer drops) live in parchmint's CLAUDE.md; these are the prep-side ones.

- **A class the library ADDS at init cannot be the evidence that the library was supposed to run.** `detect_slider_defect.js` and `wait_for_sliders.js` both used `[class*="slick-"]` to decide whether a page has a carousel worth caring about — but slick writes `slick-slide`/`slick-track`/`slick-initialized` itself, so a total init failure leaves ZERO slick-* elements and looks exactly like a page with no carousel. Measured on test-site-2, whose review carousel is slick bundled inside an Elementor add-on (so `script[src*="slick"]` misses it too): roughly **1 run in 3** came back with `.slick-initialized=0`, `.slick-slide=0`, the carousel container **11986px tall instead of 796px**, the page 17039px instead of 5849px — and the detector reported `unused: true`, no defect, no retry, shipping a broken archive ~2 MB lighter than a good one. Detect the SHAPE instead: a carousel-classed container more than 3x the viewport tall with 3+ children is stacked, whoever's library it is. That threshold is nowhere near either edge (good measures 0.9x, broken 13x), it costs nothing on healthy pages (test-site-1 and test-site-5: zero detections, unchanged 9s captures), and the existing retry machinery does the rest — the failing run now logs `evidence="stacked:1:11986:17039"` and re-captures clean.
- **Never hide by substring-matching a short class prefix — over-hiding destroys content in total silence.** `hide_overlays.js` carried `[class*="om-element" i]` for OptinMonster. `om-` is two characters and belongs to nobody: it also matches `custom-element`, `zoom-element`, and — measured on test-site-2 — a video plugin's own `keywest-element keywest-ele-1 Element om-element`, four of them, which hid the site's **hero video and every review thumbnail**. The page archived with two large blank bands, no error anywhere, in every backend, for as long as the selector existed. Two things made it hard to find: the elements are created by page JS as the player initializes, so they do not exist at `--prep minimal` and a selector audit there comes back empty; and the loss is in PREP, so a `-f png` capture of the live prepared page shows the same blanks — which is the fastest way to tell prep damage from serialization loss. Selectors here must identify the framework (`[class*="optinmonster" i]`), with `om-*` matched only as a descendant of such a root. Under-hiding is cheap: a popup that survives is still caught at capture time by `dismiss-popups` and `remove-blocking-overlays`. Over-hiding is not recoverable.
- **A cross-origin stylesheet renders but cannot be READ, and that silence is invisible until something inspects the CSSOM.** `sheet.cssRules` throws on a sheet served from another origin without CORS headers, so every step that walks the CSSOM — font extraction above all — behaves as if the sheet were empty. Measured on test-site-2: 5 of 90 sheets were unreadable and held the @font-face rules for **Orbitron, its heading typeface**, plus Ubuntu, Montserrat, Open Sans and Source Sans 3 — 9 of the 15 fonts the page actually loaded. Archives came out with the other 6 and rendered every heading in a system fallback, and the offline screenshot diff against a reference capture was **15.2%**; with `inline-crossorigin-css` fetching those sheets server-side and inlining their text, it is **2.2%**. The inlined `<style>` goes immediately after its `<link>` (document order IS the cascade) and relative `url()`s are resolved against the sheet's own address first, since the copy now lives in the document. The `<link>` stays — it is what the page declared. This never bit parchmint's former SingleFile backend, which re-fetched such sheets through its own page-context fetch bridge; everything built on Chrome's snapshot needs it done for it, which is why the gap only appeared when that backend was retired.
- **A serializer sees MARKUP, so runtime-only state has to be written back into the DOM — and that is prep's job, not the backend's.** Three steps at the very END of `Staticize` exist for this, and they must stay last, because every step above them can still change the DOM and what gets written back has to be the final state. `materialize-form-state` turns a typed value, a ticked box and a chosen `<option>` into attributes (passwords deliberately excluded — an archive is a file that gets copied around); `<details open>` needs nothing, being an attribute already. `flatten-adopted-stylesheets` emits `document.adoptedStyleSheets` as a real `<style>` — measured, constructed sheets were dropped by **every** serializer tried, Chrome's MHTML writer and SingleFile alike, because CSSOM-only state is in no one's markup. `link-shadow-styles` re-expresses each shadow root's CSS as a `<link>` to a `data:` URL, because Chrome serializes shadow roots but drops `<style>` elements inside them while keeping a `<link>` in the same position — verified with a three-way probe (`<style>` lost, `<link>` survived, `adoptedStyleSheets` lost). It **keeps** the original `<style>`: removing it would leave the live page waiting on a stylesheet to load, and the backends that photograph the page could catch the flash. All three are layout-neutral by construction, so nothing needs to settle after them. Closed shadow roots are unreachable from page script, so their styling cannot be repaired — their content still serializes, which is more than a page-script serializer manages at all.

- **A wait that starts its own observer can only ever answer prospectively, so its quiet window is a FLOOR every page pays — including the ones that finished rendering seconds ago.** Each `wait-network-idle` and `wait-quiet` used to enable the network domain / attach a MutationObserver on entry and set `lastActivity = now`, discarding everything already known about the page. Measured: the four network-idle waits, four DOM-quiet waits and the layout window cost a **flat ~3.5s on every capture regardless of the page** — 4.6s of example.com's 5.1s total, for a twelve-node document with no script. `actions.SettleMonitor` fixes it by recording continuously instead: `settle_monitor.js` goes in via `Page.addScriptToEvaluateOnNewDocument` (so it survives an age-gate reload) and one network listener attaches **pre-navigation**, both before the first request, and the waits then ask about the past. End to end through `parch`: example.com 5s → 3s, test-site-4 6s → 4s, test-site-5 8s → 7s, test-site-8 7s → 6s, test-site-1 9s → 8s, output byte-equivalent in every case, while a page that is genuinely still working (music.youtube.com, still mutating 8s in) waits exactly as long as it did. Two things this is NOT: it is not a "pre-rendered page" detector — neither served-HTML-vs-DOM size nor hydration markers separate the cases (test-site-1 carries no framework markers at all; music.youtube.com ships a large SSR shell), only the page's own recorded history does, per page, with no site list; and it does not make the quiet windows shorter, so a page that mutates late still gets caught. **A continuous monitor must also age out requests it will never see end**, which a per-wait one never had to: a cross-origin iframe's own document request is reported on the page target when it STARTS but completes on the iframe's out-of-process target, so it stays "in flight" forever. That is what a naive port of the counter did — test-site-2's twelve YouTube embeds, a youtube-nocookie embed and Google's IMA SDK bridge sat open with ages past 42s, no wait could ever see an idle network, and all four burned their full timeout: **25s of pure waiting, turning a 26s capture into 49s**. Subframe documents are excluded by frame id, and `staleAfter` is the net under every other way a request can leak (an XHR abandoned when `remove-junk-iframes` deleted its frame, a hung connection). **Corollary: never call `network.Disable()`.** Enabling is idempotent and cheap; disabling is global to the target, so a prospective wait tidying up after itself silences a monitor listening on the same page — a record with a hole in it is worse than no record. The monitor also sees prep's OWN edits, which is why a `wait-quiet` placed right after a DOM-mutating step still pays its window (~1.4s across the recipe, the largest piece left).
- **A popup suppressed only by a step that RUNS is suppressed by luck; the prep getting faster is enough to lose the race.** test-site-2's OptinMonster campaign ("Subscribe to learn more about the XCR Modular Tactical Rifle") renders **~5.5s after the scroll walk**, and it used to be caught because prep still had tens of seconds of waiting left to run after that — `dismiss-popups` and `remove-blocking-overlays` only ever see what exists at the moment they execute. Cut the dead waiting and the campaign started landing AFTER the last sweep and got baked into archives. The fix has to be race-free, which means CSS: `hide-overlays` injects its stylesheet before anything renders, and a rule there applies to elements inserted at any later time, including during serialization. **Prevention through the site's own state does NOT work here** — seeding the `om-<slug>` cookie OptinMonster writes when a visitor closes a campaign (plus `omSeen-<slug>`, `omLastSeen`, `omFoldersClosed`, all read off a live dismissal) leaves it rendering anyway, verified twice. The campaign root is `id="om-<slug>"` carrying the class tokens `Campaign` and `CampaignType--popup`; the selector requires BOTH the id prefix and the class token, and names the overlay campaign types explicitly so an inline campaign — which is page content — is untouched. Anchoring on `om-` alone is the documented disaster below; anchoring on `keywest-` is no better, since this very site carries that prefix on both the campaign and a video plugin's elements. Verified by the shape it leaves behind: the campaign still renders (13136 chars of text) at `display:none` with a 0x0 box, while the hero video, the three review thumbnails and all four Instagram tiles survive.
- **`scroll-and-wait-images` must wait for a rendering opportunity, but nothing says it has to wait a fixed 250ms per band.** The walk's cost is `steps x pause`, and steps scale with page height: test-site-7/wiki/Trilobite is 30717px — **39 steps, 10.1s** — where exactly ONE step produced any DOM mutation. The pause is now evidence-driven (floor ~2 frames + 50ms quiet, same 250ms cap), which took that walk to 3.1s, test-site-1 2.4s → 1.3s, test-site-2 2.4s → 0.8s. Two things this got wrong on the way: **an adaptive pause keyed on DOM quiet alone returns instantly and breaks the step**, because the record is retrospective — a page quiet for a second already satisfies it, so every step returns in 0ms and no band is ever painted; there must be a floor of two `requestAnimationFrame`s, since IntersectionObserver callbacks are delivered while updating the rendering and a scroll that never paints notifies nobody. And **mutations alone are the wrong signal**: native `loading="lazy"` has the browser fetch the image with NO DOM change at all, which is why test-site-7's walk looks completely inert to a MutationObserver while loading forty images — hence the `PerformanceObserver` on resource entries alongside it. Verified for loss rather than assumed: same script, `force-image-loading` + `wait-images` after it, `document.images` all complete with **identical counts and identical total megapixels** (test-site-1 49/19.62MP, test-site-8 27/0.83MP, Trilobite 75/3.24MP) old walk vs new, and `parch` archives of Trilobite came out LARGER (4.4MB → 4.9MB), not smaller. The bottom-of-page pause stays fixed: it is where a scroll-throttled loader's trailing call lands, and it is paid once.
- **Junk iframes are a capture-time COST, not just clutter.** A DOM serializer that walks frames gives every surviving iframe a full recursive pass with its own resource fetching and timeouts. Measured against parchmint's since-retired SingleFile backend, so the numbers are an upper bound — Chrome's snapshot is cheaper — but the step still earns its place by keeping tracker frames out of archives. test-site-6's five frames (a reCAPTCHA anchor, a Criteo ad-sync pixel, three srcless 0x0) cost **5.0s of a 5.4s** serialization and contributed 1.9 KB to a 6 MB archive; test-site-2 went 7.0s → 2.0s. `remove-junk-iframes` recovers all of it and must stay before `freeze-iframes`. The predicate deletes, so it is deliberately conservative — visible, sized, non-tracker frames are content (MDN's shadow-DOM live samples: `kept=4, removed=0`, all four still frozen). Widen the host list before loosening the geometry test.
- Media freezing (`capture-video-frame`, `rasterize-font-icons`) must run BEFORE the embed steps — the `<img>`s they create (posters, YouTube thumbnails) carry external URLs that still need inlining. (`rasterize-canvases` is exempt: it produces data URIs directly.)
- WebGL canvases are only readable because the `preserve_webgl_buffer.js` pre-navigation script forces `preserveDrawingBuffer` before any page JS runs; a WebGL context created without it reads back transparent black forever. Never demote it to an ordinary step.
- Chrome throttles rAF for offscreen content, and offscreen cross-origin iframes (OOPIFs) are not rasterized AT ALL by full-page screenshots — `captureBeyondViewport` included. Hence `warm-canvases` (scroll blank canvases into view until they paint; a same-process canvas keeps its last frame) and `freeze-iframes` (screenshot each cross-origin iframe WHILE it is composited in-viewport, then swap in the still). Dwelling alone is useless for OOPIFs — their pixels don't persist offscreen; the shot must happen while visible.
- **`scrollIntoView` scrolls every scrollable ancestor, not just the window — put inner scroll positions back.** A carousel's clipping box is one (`overflow:hidden` still scrolls programmatically). `focus_opaque_iframe.js` scrolls each cross-origin iframe into view for its still and used to restore only the window, so on test-site-2 the video carousel stayed parked on the last video frozen: the screenshot backends and the text layer recorded slide 10 as showing, while the carousel's own state — and the DOM-serialized archive, which cannot record `scrollLeft` — said slide 1. Text the layer called visible was clipped in the file, and `parch mark` found nothing there without `--hidden`. The script now records the ancestors it moved and restores them on the next call and in the final restore. Any new step that calls `scrollIntoView` owes the same.
- MDN-style pages put their sample iframes inside open shadow roots — any script that enumerates canvases/iframes must pierce `shadowRoot`s, or it silently finds nothing.
- `actions.BypassCSP` (pre-navigation) is load-bearing for ALL injected data: URIs. A site CSP without data: in img-src silently blocks every injected image on the live page (`complete=true, naturalWidth=0`, broken-image placeholder) — which only shows up in the live-rendering backends (pdf/png/jpeg/webp), because saved HTML carries no CSP header and renders the same data URIs fine. test-site-4 (default-src 'self') is the reference case; debug with `document.querySelector('img').naturalWidth`.
- Server-side fetchers must NOT set `Accept-Encoding` manually — it disables Go's transparent gzip decompression and gzip-served SVGs get embedded as compressed garbage.
- `inject_images.js` removes `<source>` siblings inside `<picture>` — otherwise the external source keeps winning over the injected data URL.
- **Never freeze an image's RENDERED box as `width`/`height` attributes.** Those attributes are *presentational hints*: they apply as CSS to whichever axis the page's own stylesheet leaves `auto`. On a responsive image (`width:100%`, height from `aspect-ratio`) the width stays fluid while the height stays nailed to the capture viewport, so the picture distorts at every other window width — and in both directions: test-site-3's promo tiles rendered 340x604 instead of 340x453 at 1200px (33% too tall) while its carousel slide rendered 1248x546 instead of ~970x546 at 1920px (29% too wide). It is NOT format-specific; HTML and MHT both carried it, and it is invisible at exactly the capture width, which is where it hid. Freeze pixels only for images laid out at their bitmap's own size; otherwise preserve the intrinsic RATIO, and only when the page dictates none. Both dimensions must always come from one source (mixing the page's value for one axis with the bitmap's for the other turned round avatars into ovals).
- Never remove elements matched by class alone without a structural guard — sites put state classes like `age-gate-open` on `<body>`.
- An age-gate click can trigger a reload: `actions.WaitForReady` absorbs it, and injected CSS must be re-applied afterwards.
- **`goodblaster/errors.Wrap(nil, msg)` returns a NON-NIL error.** Never tail-return `errors.Wrap` unguarded.
- **An event listener must not run a command.** `chromedp.Listen` callbacks run inside the loop that reads the tab's messages; a command issued there waits for a reply only that blocked loop can deliver. The JS-dialog auto-accept answers from its own goroutine for this reason — doing it inline hung the session until the timeout on any page that called `alert()` during load.
- **Chrome's sandbox is never dropped silently.** On a host that restricts unprivileged user namespaces (Ubuntu 23.10+, every hosted CI runner) or as root in a container, Chrome exits with "No usable sandbox". `PSCRIPTION_NO_SANDBOX=1` is the explicit opt-out; it is not a default and not inferred, because the sandbox is what stands between a hostile page and the machine.
- **Log through `internal/log`, and log an error's TEXT.** Library code that called `logos` directly bypassed the seam, and `With("error", err)` renders an error value as `{}` — every failed fetch logged `error={}` and the reason a resource went missing was never visible. Use `log.With("reason", err.Error())` or `log.WithError(err)`. The CLI configures the logos default logger once; nothing may reset it afterwards (an init helper that did is how debug lines leaked out of `pscribe` without `-v`).
- **A pre-navigation action that returns an error fails the session.** `PreseedConsentCookies` errored on a hostless URL, so a `file:` page could not be captured at all; anything that is merely inapplicable must return nil.
- **A fetch that failed once is not retried a few seconds later.** `PrefetchCache.take` reports a real failure as known-failed; only a fetch that never ran (context ended) falls back to a fresh one. Refetching sent two identical doomed requests for every hotlink-protected image.
- **Server-side fetches are capped** (`maxResourceBytes`) and carry the capture context. A resource becomes a base64 data: URI held in memory; an endless response must fail, not be read to the end — and it must fail rather than truncate, since a truncated image embeds as a corrupt one.
- **`dismiss-popups` closes only MODAL `<dialog>`s** (or ones named like an overlay). A non-modal `<dialog open>` is a content panel the page chose to show; closing every `dialog[open]` deleted those from archives.
- **`preserve-hidden-attr` is a snapshot-backend step, not a Staticize step.** It unhooks the page's own `[hidden]` selectors (freezing the computed result inline), which is harmless a moment before a snapshot and pointless damage for a backend that photographs the live page. See parchmint's "Hidden text".

## Verification

Prep changes are exercised end-to-end through parchmint: build `parch` from this repository (one module, so changes here are picked up directly) and run the reference-site verification described in parchmint's CLAUDE.md. For script-only work, `pscribe --prep staticize -v <url>` shows per-step logs and timings.

## Conventions

- Error wrapping via `errors.Wrap(err, "context")` (github.com/goodblaster/errors) — guarded, see invariant above.
- New prep behavior = a named pipeline step (JS file → `ScriptFile` constant in `scripts/embed.go` → action wrapper → step in `pipeline/staticize.go` + `Register`), not inline workflow code.
- Scripts return a small stats object; it lands in step logs.
- CLI: logs → stderr, content → stdout/file.
- **Flags use [spf13/pflag](https://github.com/spf13/pflag)**, matching parchmint, and the names are parchmint's wherever both have the option: `--recipe`, `--profile`, `--show`, `--timeout`, `--width`, `--height`, `--dpr`, `--user-agent`, `-v`. (`-r` still works for `--recipe`, deprecated: in `parch find` it means recursive.) Exit status follows parch too — 2 for a bad invocation, 1 for a run that failed. Multi-character flags take two dashes. pflag parses flags anywhere on the line, which is why `pscribe URL @links --only links` works and why no flag-reordering helper is needed.
